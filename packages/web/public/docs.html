LOAD-BEARING DESIGN

Core primitive and ecosystem

Core primitive

TEMPO is a machine-native opening and continuous-liquidity service for rolling Event Contracts. It converts market birth into an explicit, agent-operated opening auction and carries the position lifecycle through verified settlement and claim.

Why Somnia

Somnia's live log tail, reactivity path, fast blocks, and native transaction delivery make event-to-decision-to-order operation practical at rolling-window cadence. Removing that path degrades the product into delayed polling.

Why DreamDEX

The one-book/two-outcome CLOB, opening boundary, mint/burn pair inventory, live grid parameters, explicit expiries, finalized registry, and redemption API directly define both agent policies.

Why Event Contracts

Birth, binary boundary, expiry, oracle resolution, void handling, claim, and roll are the lifecycle. Without Event Contracts, the opening mechanism and settlement automation do not exist.

IDENTITY RULE

State is keyed by marketId or symbol, never pool address, because DreamDEX pools are recycled across rolling windows.

TWO KEYS / TWO POLICIES

Autonomous firm

01

GENESIS

MAKER

Anchors newborn windows with a two-sided probability quote. It buys UP plus DOWN to cold-start empty inventory, then sells held UP inventory when appropriate.

  • Post-only orders
  • Adaptive half-spread as time decays
  • Inventory-skewed quote center
  • Cancel-and-replace with churn avoidance
  • Stops before the configured endgame gate
02

VECTOR

TAKER

Independently evaluates the same window and only crosses when the displayed touch diverges from its estimate by more than its edge threshold.

  • IOC orders; remainders never rest
  • Independent volatility horizon
  • Book-size and collateral caps
  • UP and complementary DOWN opportunities
  • Explicit stand-down decisions

Coordination contract

Each agent has a distinct signer, ledger, policy, and executor. They share discovery and a RiskEngine, but cannot self-match because keys are required to differ. All actions and stand-down decisions are journaled.

WINDOW STATE MACHINE

Market lifecycle

  1. BIRTHA new market ID appears in the rolling series.
  2. ANCHOROpening boundary, spot, book parameters, and balances are acquired.
  3. GENESISThe maker prepares the initial two-sided anchor.
  4. REPRICELive feed and book events trigger new estimates and quote maintenance.
  5. ENDGAMERisk gates tighten as expiry approaches.
  6. LOCKTrading closes; no further mutations are allowed.
  7. SETTLEThe resolved or voided outcome is read from chain/indexer truth.
  8. CLAIMThe paying side is redeemed; both sides are redeemed for voided markets.
  9. ROLLThe finalized window leaves the live list and its successor takes over.
DETERMINISTIC ESTIMATION

Appraiser and estimates

The appraiser computes P(close >= strike) under a driftless diffusion. Inputs are the official live spot, the on-chain opening boundary, realized volatility from timestamped feed observations, and seconds remaining.

import { fairValue, realizedVolPerSqrtSec } from "@tempo/core";

const sigma = realizedVolPerSqrtSec(feedTicks);
const estimate = fairValue({
  spot: liveSpot,
  strike: onchainOpeningPrice,
  sigmaPerSqrtSec: sigma,
  secondsLeft,
});

// estimate.p and estimate.band are QUANTITATIVE ESTIMATES, never chain facts.
OutputMeaning
pEstimated probability of the UP outcome.
dLog-distance from strike in remaining-window volatility units.
bandOne-sigma probability range around the estimate.
expectedMoveOne-sigma underlying move over the remaining time.
NO FALLBACK VOLATILITY

If sufficient real feed history is unavailable, the estimate is NO DATA. TEMPO never substitutes a demo volatility.

@TEMPO/CORE 0.3.0

Core SDK

@tempo/core is the reusable Node 20+ ESM SDK, distributed as a compiled GitHub Release artifact with TypeScript declarations. It consumes @somnia-chain/markets-sdk exactly at version 0.29.0.

npm install https://github.com/Kevincruz2005/Tempo/releases/download/sdk-v0.3.0/tempo-core-0.3.0.tgz

Read-only market client

import { loadConfig, TempoExchange } from "@tempo/core";

const config = loadConfig();
const exchange = new TempoExchange({ config });

try {
  const markets = await exchange.markets();
  const market = markets[0];
  if (!market) throw new Error("NO DATA");

  const chain = await exchange.onchain(market.marketId);
  const [params, book, spot, opening] = await Promise.all([
    exchange.bookParams(chain.pool),
    exchange.book(market.upSymbol, 5),
    exchange.spot(market.asset),
    exchange.openingPrice(market.marketId),
  ]);
} finally {
  await exchange.close();
}

COLD-PATH LEARNING FROM FACTS

Calibration loop

After claim sweeps, TEMPO selects at most the latest 30 resolved, non-voided markets and scores the closest eligible pre-expiry estimate. A bounded temperature model minimizes Brier loss on that real settlement window. One fingerprinted window can produce only one epoch; --force bypasses the 25-market size gate but never the empty or duplicate-window gates.

npm run cli -- calibrate
npm run cli -- calibrate --force

Only sigmaMultiplier and takerEdge move, each clamped to 0.5x–2x its environment default. VECTOR direction is evaluated against settlement before edge adjustment. Risk caps never change. Every epoch records model/version, temperature, input fingerprint, old/new parameters, Brier before/after, directional metrics, clamp status, and reason.

QUANTITATIVE ESTIMATE / CHAIN FACT

The probability and learned calibration are estimates. Settlement is an on-chain fact. Safety remains deterministic and external to the model; unavailable evidence cannot trigger an epoch.

HUMAN SIGNER / EIP-6963

Connect wallet

The dashboard connects an EIP-6963 provider, falling back to window.ethereum. It displays only the connected address (truncated), real chain id, and native balance. Active chain metadata comes from server configuration rather than a browser constant. TEMPO never receives a seed phrase, private key, or agent key.

Network and activity

Somnia Shannon testnet is chain 50312; mainnet is 5031. A wrong-network banner offers a wallet chain switch. Account, chain, and provider disconnect events clear local state. Fills and orders are attributed read-only through the markets SDK live store.

One guarded action

The IOC review calls buildWalletOrder, checks collateral/native balances, and validates every destination against configured protocol/live-market addresses. It shows market, side, size, limit, expiry, cost, available balance, chain, destinations, value, risk verdict, and status 1. Review never signs: a separate Confirm in wallet action is required.

NO BLIND SIGNING

Account/network changes, insufficient funds, expiry, bad destinations, malformed provider data/hashes/receipts, rejection, cancellation, and disconnect stop the flow. No browser path can access GENESIS or VECTOR keys.

DEFENSE IN DEPTH

Security model

TEMPO has no SQL database or query-construction layer, so SQL injection is absent by architecture. Controls focus on the actual signer, chain, HTTP, browser, and dependency boundaries.

Signer boundary

Keys remain server-side, are optional, must differ by agent, and are never returned by the state API.

Chain boundary

Firm plans are risk-gated. Trading mutations re-read live status and enforce tick/lot, expiry, and receipt checks.

Network boundary

Loopback bind by default, Host and same-origin checks, GET-only routes, URL/header/time bounds, and per-IP rate limits.

Streaming boundary

Total and per-IP SSE caps, heartbeat, backpressure cleanup, and defensive browser parsing.

Browser boundary

CSP, frame denial, MIME sniff prevention, isolation headers, output encoding, fixed classes, and HTTPS-only audit links.

Transport boundary

Recursive credential-key redaction, depth/cycle limits, generic server errors, and no-store API responses.

File boundary

Decoded path containment rejects traversal, dotfiles, backslashes, and malformed encodings.

Supply chain

The markets SDK is exactly pinned at 0.29.0; the recorded npm audit reports zero known vulnerabilities.

Emergency control

TEMPO_PAUSED=true refuses every write before SDK submission. Dry-run remains the default.

CI runs repository secret scanning, strict TypeScript, offline/security tests, critical-core coverage, dependency audit, and package inspection. Rotation and compromised-key procedures are in docs/SECURITY.md. TEMPO deploys no custom contract, so custom-contract access-control and reentrancy scanners are not applicable.

REMOTE DEPLOYMENT

The built-in server is an operator-local surface, not a public identity system. Remote access requires TLS, authentication, authorization, and ingress restriction at an audited proxy.

OPERATIONS

Deployment and failures

No custom contract deployment is required. TEMPO uses the official Somnia/DreamDEX deployment through configuration, two distinct funded accounts for live operation, and local JSONL storage for evidence.

Live-operation checklist

  1. Run npx tsx probe/live-probe.ts and treat its output as connectivity truth.
  2. Set two distinct private keys and fund both with native STT for gas.
  3. Run npm run faucet for testnet collateral.
  4. Review risk limits and keep TEMPO_DRY_RUN=true for the first firm run.
  5. Inspect journal decisions, balances, live status, tick/lot, and venue ID.
  6. Set TEMPO_DRY_RUN=false only for intentional signed operation.
  7. Run tempo verify to independently check recorded receipts.

COMMON WORKFLOWS

Examples and FAQ

How do I inspect without trading?

Leave keys empty and run npm run cli -- markets, book BTC, or firm simulate.

How do I stop every write?

Set TEMPO_PAUSED=true and restart. The core refuses writes even when a signer exists.

Can an MCP client choose a contract?

No. It chooses a bounded market reference; Tempo resolves and chain-gates it. No arbitrary destination or signer argument exists.

Are estimates oracle facts?

No. Fair value, volatility, calibration, and agent plans are labeled estimates. Status, settlement, balances, and receipts are facts.
